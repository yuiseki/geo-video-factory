# 資料から台本を書く

報道、論文、自治体の資料、Web の記事などを元に、掛け合いや見出しを書くときの決まり。

## 事実の扱い

- 台本に入れてよい事実は、元にした資料に書かれていることだけ。推測や評価を、事実と同じ口調で言わない。言うなら「〜と考えられている」「〜という説がある」と、誰の見方かを添える。
- 数字、日付、人名、地名は原文の表記と値のまま使う。単位の換算や丸めをするなら、元の値をメモに残す。
- 原文の文章を長く引き写さない。要約して自分の言葉にする。そのまま引くときは `quote` で、媒体名と日付を添える。
- 同じ出来事を扱う資料が複数あれば、1 つの話題にまとめ、出典はすべて残す。
- 「衝撃」「速報」のような煽りの言葉を、見出しにもセリフにも使わない。
- 外国語の資料を訳すときは、固有名詞を日本の報道で一般的な表記にそろえる。

## 出典の書き方

- 出典の名前は、記事を出した媒体 (発行者) にする。配信を中継したサイトや、まとめたフィードの名前ではない。URL のドメインから判断し、分からなければ記事の中の発行者の表記を見る。
- 出典ごとに、媒体名、原題、URL を記録する。概要欄に出すときもこの 3 つを使う ([publishing.md](publishing.md))。

## 生成した文の後処理

言語モデルに台本や要約を書かせると、表示や読み上げで困る文字が混ざることがある。採用する前に機械的に取り除く。

- Markdown の残り (`**`、`__`、`[文字](URL)`)。
- 絵文字。
- 日本語の文に紛れ込んだハングル (数詞の「십」「만」などが混ざる例があった)。数詞なら漢字に戻す。
- Unicode の NFKC 正規化をかけると全角のコロンなども半角になるので、画面に出す文は必要な記号を全角に戻す。

## 言語モデルに書かせるとき

- 出力は JSON Schema で形を決め、スキーマに通らなければ採用しない。見出しや要約の文字数の上限も、スキーマかその後の検査で確かめる。
- 台本を書かせるだけなら、ファイルの読み書きやコマンドの実行などの道具 (ツール) を渡さない。入力の資料に指示文が紛れていても、それ以上のことができないようにする。
- 方針に合う資料が無いときに「何も選ばない」を許すと、空の出力を正常として扱ってしまう。作るか作らないかの判断は、呼び出し側でする。
