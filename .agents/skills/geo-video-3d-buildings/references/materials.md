# テクスチャと建物単位の疑似外観

## 写真テクスチャの軽量化

形状、UV、Draco圧縮を維持し、埋め込み画像だけを縮小する。近景tileは最大2048px、遠景tileは1024px程度から試し、WebP品質は80台後半を基準に目視比較する。

1. GLB の image と bufferView を読む。
2. 埋め込みWebPをデコードし、必要なものだけ縮小する。
3. bufferView と bin chunk を再構築する。
4. JSON/BIN chunk の4byte境界を保つ。
5. RTC中心を manifest に退避済みであることを確認する。

元画像と最適化後のサンプルを同じカメラで比較し、看板や特徴的な外壁が潰れていないか確認する。

## 明るすぎるテクスチャ

texture atlas を小さく縮小して輝度分布を調べる。明るい画素の比率や平均輝度が高い材質だけを抑える。既存試作では、明るい画素比率が約0.42超または平均輝度0.74超なら係数0.64、約0.24超または平均0.64超なら0.78が調整の出発点になった。

全材質へ一律に暗色化をかけない。写真テクスチャの色差を残し、白飛びに近い atlas を選択して処理する。

写真テクスチャが全体に暗い、推定の外壁が明るいといった、面の種類の間の差は別の問題である。地面の空中写真を基準にそろえる ([tone.md](tone.md))。

## なぜ材質単位の模様では不足するか

PLATEAU の複数建物が同じ material を共有する場合、material UUIDだけを乱数種にすると隣接建物へ全く同じ色と模様が連続する。現実の街並みとして目立つ違和感になる。

glTF の `_BATCHID` は建物単位の識別に使える。Three.js の geometry attribute では小文字化された `_batchid` も確認する。shader へ batch ID を渡し、material seed と組み合わせて建物単位の決定的な値を作る。

## 疑似外観

無彩色に近い面へだけ、建物IDを種にした弱い変化を加える。

- 暖色・寒色の微差
- 明度差
- 約2.9〜3.55mの階高
- 約3.5〜5.3mの窓間隔
- 暗い窓と細い階境界
- 屋根の約6.5〜9mグリッド、継ぎ目、設備らしい小領域

数値は実測復元ではなく視覚的な出発値である。実在する窓や設備を再現したとは表現しない。

元テクスチャの chroma が高いほど疑似外観の影響を弱める。写真由来の看板や外壁色を保ち、灰色や白に近い低情報面だけを補う。

乱数は時刻やフレーム番号から作らない。同じ建物IDから常に同じ結果を出し、動画のちらつきを防ぐ。

## 屋上に空中写真を貼る

- テクスチャの無い PLATEAU の屋上には、manifest の `roof_texture` (地理院オルソ) が貼られる。
- テクスチャのある建物の屋上にも貼る設定がある (`plateauBuildings.roofPhoto: "all"`)。近景だけ超解像した写真を重ねる `roofPhotoNear` と、その高さより上の屋上は元のテクスチャのままにする `roofPhotoMaxZ` (シーンの z、標高そのものではない) もある。既定は切ってある。
- 渋谷 (2026-11-25) では、元のテクスチャのある屋上に貼ると悪くなった。地理院のシームレス空中写真では高い建物が外側へ倒れ込んで写るため、屋上の真上の画素が隣の地面や壁になる。PLATEAU の屋上テクスチャは薄く粗いが、位置は合っている。元のテクスチャを優先するという PLATEAU++ の順序どおりにする。

## 目視項目

- 同色の建物が連続していないか。
- 同じ窓パターンが帯状に反復していないか。
- 疑似模様が屋根と壁をまたいでいないか。
- 近景で模様が巨大または細かすぎないか。
- 遠景で全体が灰色の塊に戻っていないか。
- カメラ移動中に模様や色がちらつかないか。
