# 作業手順書・分岐計画・撤退基準 (`plateau-reality-view`)

この文書は、[README.md](README.md) で整理した「PLATEAU++ と実写真から作る暗黙的・生成的ワールドモデル」を検証するための具体的な実行手順書です。
各段階（Stage 0〜Stage 4）の終わりに**定量ゲート**を置き、結果によって次の経路へ進むか、別経路へ切り替えるか、実験自体から撤退するかを機械的に決めます。

---

## 0. 全体フローと分岐図

```text
[Stage 0: 渋谷テストベッド・Hold-out 実写真・採点スクリプトの固定]

   ▼

   ├─ 最小モデルすら資源上限内で動かない ────────────────────► [撤退 R1]
   ├─ 幾何・時間一貫性とも合格（オフライン用途で十分） ────────► [Stage 4: 統合・再現性検品]
   └─ 幾何は保てるが看板劣化・チャンク境界ドリフト・速度不足 ─┐
                                                              ▼
[Stage 2: 経路 B — Leave-One-Out 自己教師ペアによる 1〜4 NFE 生成修復器]

   └─ 1〜4 NFE で品質・時間一貫性とも合格 ─────┬─ (決定論・実用優先) ───────────────────────────────► [Stage 4]
                                               └─ (リアルタイム・メッシュレス推論まで挑戦) ─────────┐
                                                                                                    ▼
[Stage 3: 経路 C — 地区特化・小型 Conditional Mean-Flow 自己回帰ワールドモデル]
```

## 1. Stage 0: ベンチマークと採点器の固定（着手初日）

モデルを動かす前に、比較の土俵と自動採点器を固定します。新規のデータ収集は行わず、すでに実写真・カメラ姿勢・3D 建物が揃っている**渋谷スクランブル交差点〜センター街入口（原点 `139.7005, 35.6595`、半径 `250 m`）**を唯一の実験場にします。

### 手順 0-1: 入力データの準備と Hold-out 分離

1. **PLATEAU++ の用意**:
   `packages/pipeline` から `OVERPASS_URL=<自前の Overpass> python -m buildings.plateau_pp --bbox=139.6975,35.6575,139.7035,35.6615` を実行し、共有キャッシュ（`$GEO_VIDEO_CACHE`）上の `manifest.json` と `tris.npz`（`buildings/plateau_mesh.py`）を確認する。
2. **写真とカメラ姿勢の選別**:
   既存の渋谷プロジェクト（`projects/2026/11/20/liminal-space-city-walk-with-bgm/`）で位置合わせ済みの `cams.json` から、`photos/photo_guard.py` を通過する CC0 / CC BY 写真だけを残す（昼レイヤーを第一対象とし、昼で成功するまで夜へ広げない）。
3. **Hold-out 評価写真の隔離**:
   スカイライン費用 `< 0.8` かつ `overlay_check.py` で建物の輪郭一致を目視確認した地上・俯瞰写真から **6 枚（地上 4 枚、高所俯瞰 2 枚）を `holdout_cams.json` に分離**する。この 6 枚は `world_model` のアトラス構築にも Stage 2/3 の学習にも一切入れない。
4. **比較ベースラインの作成**:
   残りの写真（`train_cams.json`）だけで `world_model/build_atlas.py` と `pp_scene.py` を回し、**現行ベースライン（明示的 `PLATEAU++` + `world_model` アトラス）** の `.blend` シーンを固定する。

### 手順 0-2: 標準カメラ軌道 3 本の定義 (`eval_tracks.py`)

`world_model/world_camera.py` の形式で、性質の異なる 3 本のカメラ軌道（各 24 fps × 10 秒 = 240 フレーム、解像度 `832×480` と `1280×720` の 2 系統）を定義する。

| 軌道 ID | カメラの動き | 確かめたいこと |
|---|---|---|
| `track_elevated` | **Tesla Reality View 型**: 地上を毎秒 4〜6 m で進む仮想車両／歩行者の斜め後ろ上空（高さ 15〜22 m、俯角 30〜40°）から追従する三人称俯瞰 | 本実験の主目的。屋根・壁・路面が同時に映る俯瞰で立体感と進行方向の一貫性が保てるか |
| `track_interp` | `train_cams.json` の観測が密な交差点内を、人の目の高さ（1.6 m）でゆっくり横断する軌道 | 実写観測が豊富な領域で、既存の `world_model` の看板や細部を劣化させないか |
| `track_extrap` | 交差点からセンター街の路地へ入り、視線角が浅い壁（`min_cos` が厳しい区間）と未観測面（`seen == 0`）を正面に見る軌道 | 既存 `world_model` が斜めの縞や灰色の壁になる区間で、自然な外壁・店先を補完できるか |

### 手順 0-3: 自動採点スクリプトの作成 (`metrics.py`)

目視の前に機械で落とせるよう、次の 4 指標を計算するスクリプトを作り、まず現行ベースラインを採点して基準値を記録する。

1. **`skyline_iou`（幾何保持率）**:
   PLATEAU の `tris.npz` から `surface_atlas.depth_buffer` で求めた「建物 vs 空」の正解バイナリマスクと、生成フレームから抽出した空マスクの IoU（昼フレームで計測）。
2. **`holdout_lpips` / `holdout_psnr`（未見視点の再構成精度）**:
   `holdout_cams.json` の 6 視点から描いた画像と、人物・車両消去済みの実写真（地上 2.5 m より上の建物領域マスク内）との LPIPS および PSNR。
3. **`warp_rmse`（3D 時間一貫性・ちらつき量）**:
   フレーム $t$ の画素を PLATEAU 深度と既知カメラ行列でフレーム $t+1$ へ再投影（遮蔽境界と空を除く）したときの RGB 二乗平均平方根誤差（0〜255 スケール）。静止都市なのに模様が毎フレーム変化するとこの値が跳ね上がる。
4. **`color_drift`（自己回帰ドリフト量）**:
   1 本の軌道（240 フレーム）の先頭 24 フレームと末尾 24 フレームの平均輝度・彩度・コントラスト変化率。

## 2. Stage 1: 経路 A（ゼロ学習・G-Buffer 条件付き動画生成スパイク）

学習を一切行わず、既存のオープンな制御付き動画生成モデルに PLATEAU++ の幾何バッファを渡すだけで「Reality View 風の自己回帰チャンク生成」がどこまで通用するかを最短で測ります。

### 手順 1-1: 候補モデルのライセンス・資源監査

`models_manifest.json` を作り、次の基準を満たすモデルだけを候補にする。

- **必須ライセンス**: Apache-2.0（例: `Wan2.1-Fun-1.3B-Control`、`Wan2.2-TI2V-5B`、`Wan2.2-VACE` 系など公式カードで Apache-2.0 が明記されたもの）または CreativeML Open RAIL++-M。
- **事前メモリ見積り**:
  - 利用可能 VRAM が **16〜24 GB クラス（または統合メモリ 32〜64 GB）** の場合: `1.3B`〜`5B` モデル（FP16 または FP8）を上限とし、`14B` フル精度は最初から除外する。
  - 利用可能 VRAM が **48 GB 以上** の場合のみ `14B` 系（VACE / Control）を比較対象に含める。

### 手順 1-2: G-Buffer 条件列の書き出しとチャンク自己回帰推論

1. Stage 0 の 3 軌道（まず `track_elevated` の先頭 81 フレーム）について、Blender または `surface_atlas` からフレームごとの条件画像を書き出す：
   - **粗外観 (`coarse_rgb`)**: 現行ベースライン（`PLATEAU++` + `train_cams` アトラス）の描画
   - **深度 (`depth`)**: カメラからの逆数深度を正規化した画像
   - **観測マスク (`seen_mask`)**: 実写真が見えている画素（`seen > 0`）と未観測／浅角度画素を分けるマスク
2. 条件付き動画生成ワークフロー（ComfyUI API `$COMFY_URL` または `diffusers` スクリプト）を組み、1 チャンク（49 または 81 フレーム）を生成する。
   - 2 チャンク目以降は、**前チャンクの末尾 1〜4 フレームを開始画像（または潜在条件に軽微なノイズを足した状態）** として引き継ぎ、240 フレーム（3〜5 チャンク）までつなぐ。
   - Denoise 強度は `0.35`、`0.55`、`0.75` の 3 水準を振る（`1.0` にすると `PLATEAU++` の色や実写看板が完全に消えるため、`coarse_rgb` を潜在の初期値に残す設定も併せて試す）。

### Stage 1 の分岐判定

| 観測された結果 | 次のアクション |
|---|---|
| **A-1**: 最小モデル（1.3B、FP8/オフロード込み、`832×480`）でも OOM が解消しない、または 1 フレームあたり **5 秒超** かかり改善の見込みがない | 動画 DiT の直接推論を断念。軽量な画像ベース 1〜4 NFE 修復モデルを使う **Stage 2（経路 B）** へ進む（Stage 2 でも 5 秒/フレーム超なら **撤退 R1**）。 |
| **A-2**: Denoise を下げると（`<= 0.4`）未観測面の箱っぽさが消えず、上げると（`>= 0.6`）建物の形が歪む（`skyline_iou < 0.85`）か実写看板が別言語のような謎文字に化ける | 汎用動画モデルの事前分布と日本の都市景観の乖離が原因。`seen > 0` を保護しつつ日本の実写真ペアで学習する **Stage 2（経路 B）** へ進む。 |
| **A-3**: 1 チャンク目は良いが、3 チャンクつなぐと彩度飽和・白飛び・霧化（`color_drift` 大）が起きる | ①前チャンク引き継ぎフレームへのヒストグラム整合（カラーマッチング）と ②各チャンク先頭への `coarse_rgb` 再注入を 1 回だけ試す。直らなければ自己回帰動画生成に見切りをつけ **Stage 2（経路 B）** へ進む。 |
| **A-4**: 3 軌道すべてで `skyline_iou >= 0.90`、`warp_rmse` と `holdout_lpips` がベースラインを上回り、3 チャンク連結も破綻しない | オフライン生成パイプラインとして成立。リアルタイム性・高速化が不要なら **Stage 4** へ直行し、1〜2 NFE 化したい場合のみこの出力を教師データにして **Stage 3** へ進む。 |

## 3. Stage 2: 経路 B（自己教師ペアによる 1〜4 NFE 生成修復器の学習）

経路 A で見えた「汎用モデルのハルシネーション」「推論の重さ」「看板の劣化」を解く本命アプローチです。`world_model` を使って**位置が厳密に揃った「劣化レンダリング $X$ → 本物の実写真 $Y$」のペア**を自動生成し、1〜4 ステップで動く軽量な条件付き修復器（Difix3D+ 型）を学習します。

### 手順 2-1: Leave-One-Out ペアデータセットの自動構築

1. `train_cams.json`（渋谷のほか、`liminal-space-city-walk-with-bgm/research/tokyo_cc0/` にある丸の内・銀座・秋葉原・新宿等の位置合わせ可能な CC0 写真があれば追加可）の各写真 $i$ について：
   - **正解 $Y_i$**: `people_removal.py` で人物・車両を消した実写真（および LaMa で塗った領域を示す `inpaint_mask_i` — 損失計算から塗り跡を除外するため）。
   - **入力 $X_i$**: 写真 $i$（および視線方向が 15° 以内の近傍写真）を除いて作った部分アトラス＋`PLATEAU++` を、写真 $i$ と**まったく同じカメラ内部・外部パラメータ**で描画した `coarse_rgb_i`、`depth_i`、`normal_i`、`seen_mask_i`。
   - さらにデータ拡張として、ランダムな矩形・角度マスクで `coarse_rgb_i` の一部を `PLATEAU++` の素の壁色や浅角度引き伸ばし画像に置き換え、「未観測面・引き伸ばし面を本物の日本のビル外壁・店先に直す」課題を模擬する。
2. **位置ずれフィルタ**:
   カメラ姿勢のわずかな誤差（数度）がそのまま学習ボケにならないよう、`coarse_rgb_i` と $Y_i$ の建物スカイライン誤差が大きいペアを機械的に弾き、必要なら 2D の微小アフィン／光学フロー整合を通した `512×512` クロップ群（目標 2,000〜10,000 パッチ）を作る。

### 手順 2-2: 1〜4 NFE 条件付き修復モデルの学習

計算資源に合わせて次のどちらか 1 つを選び、単一ホストで **最大 12〜24 GPU 時間以内** で学習する。

- **構成 B-fast（推奨・省メモリ）**:
  Apache-2.0 の少数ステップ潜在画像モデル（`FLUX.1-schnell` / `Z-Image-Turbo`、または `SDXL-Turbo` / `SDXL Base` + Rectified Flow / LCM 相当の軽量 LoRA + ControlNet/Adapter）をベースにし、入力チャンネル（または Control Adapter）に `[coarse_rgb, depth, seen_mask, warped_prev_frame]` を与え、**1〜4 NFE** で $Y_i$ の潜在を予測するよう LoRA / Adapter のみを学習する（損失は `1 - inpaint_mask` 領域での L1 + LPIPS、または Flow Matching / MeanFlow 損失）。
- **構成 B-scratch（外部重み最小化）**:
  オープンな VAE（`sdxl-vae` または `wan-vae`）の固定潜在空間上で、`60M〜150M` パラメータの小型 UNet / DiT を **Conditional MeanFlow**（[Stage 3](#4-stage-3-経路-c地区特化小型-conditional-mean-flow-ワールドモデル) と同じ目的関数）で学習する。

### 手順 2-3: 時間一貫性の付与と「3D 書き戻し」分岐

240 フレームの軌道を推論する際、毎フレーム独立に推論すると未観測面の窓の数などがちらつく可能性がある。これを次の 2 段階で抑える。

1. **前フレーム 3D ワープ条件（オンライン推論）**:
   フレーム $t-1$ の生成画像を PLATEAU 深度でフレーム $t$ の視点へ再投影した `warped_prev` と非遮蔽マスクを条件に入れ、前フレームで生成した外壁ディテールを引き継ぐ（Tesla Reality View の「前フレーム＋ノイズからデノイズ」の幾何明示版）。
2. **分岐 B-2（3D アトラス / 3DGS への書き戻し蒸留 — ちらつきが出た場合の切り札）**:
   オンライン推論で `warp_rmse` が基準を超えた場合、軌道上の代表キーフレーム（例: 20〜30 枚）だけをこの修復器で高品位に生成し、それを「仮想の追加写真」として `world_model/build_atlas.py`（または 3D Gaussian Splatting）へ**書き戻して 3D シーンを更新**し、最終動画は Blender / ラスタライザから決定論的に描く。

### Stage 2 の分岐判定

| 観測された結果 | 次のアクション |
|---|---|
| **B-1**: Hold-out 6 視点で `holdout_lpips` が現行ベースライン（素の `PLATEAU++` + `train_cams` アトラス）より改善しない、または等倍目視で看板・外壁の違和感が悪化する | カメラ位置合わせ残差とデータ量の限界。位置ずれフィルタを厳格化して 1 度だけ再学習し、それでも改善しなければ **撤退 R4**。 |
| **B-2**: 単フレーム品質（`holdout_lpips`）と `track_extrap` の未観測面補完は明確に改善したが、連続再生すると微細なちらつき（`warp_rmse` 悪化）が残る | 上記の **分岐 B-2（3D アトラスへの書き戻し）** を採用する。これで時間方向のちらつきは構造的にゼロになり、描画も 1.5 秒/フレームに戻る。リアルタイム暗黙推論（Stage 3）は見送り、**Stage 4** へ進む。 |
| **B-3**: 前フレーム 3D ワープ条件つき 1〜4 NFE 推論だけで、`holdout_lpips` 改善・`skyline_iou >= 0.90`・`warp_rmse` 合格・推論 5 秒/フレーム以内をすべて達成 | 「PLATEAU ガイド付き生成的 Reality View」として合格。このまま **Stage 4** で仕上げてよい。さらに「推論時のメッシュ描画すら省いた純暗黙 Mean-Flow モデル」の可能性も確かめたい場合のみ **Stage 3** へ進む。 |

## 4. Stage 3: 経路 C（地区特化・小型 Conditional Mean-Flow ワールドモデル）

Tesla Reality View のアーキテクチャ（**視覚エンコーダ UVE + 前フレーム条件付き Mean-Flow による 1〜2 NFE チャンク生成**）に最も近い、メッシュレス推論の実験です。Stage 2 までの成果（または既存の `world_model`）を「オフライン教師データ生成器」として使い、渋谷スクランブル交差点エリア全体を暗黙的に記憶・補間する小型モデルを蒸留します。

### 手順 3-1: 軌道潜在データセットの事前キャッシュ

学習中に毎回 VAE や視覚エンコーダや Blender を回すとメモリも時間も足りないため、すべて事前にディスクへ書き出す。

1. 渋谷交差点周辺（半径 180 m、高さ 1.5〜35 m）で、ランダムな前進・旋回・俯瞰追従のカメラ軌道を **1,000〜2,000 クリップ（各 17 または 33 フレーム、`512×288`〜`640×360`）** 生成し、Stage 2 の完成パイプライン（または `world_model`）で教師フレーム列を描画する。あわせて実写真（`train_cams.json`）も長さ 1 の静止クリップとして混ぜる。
2. 全フレームを固定 VAE Encoder で潜在表現 $z \in \mathbb{R}^{C \times H' \times W'}$ に変換して保存する。
3. 基準写真群（交差点を囲む代表的な 16〜32 枚の実写真）を Apache-2.0 の固定視覚エンコーダ（`DINOv2` ViT-B/14 等）に通し、各写真のカメラ姿勢（Plücker 光線座標 $r = (o \times d, d)$）を付与した**シーントークン列**として保存する（Mini-UVE）。

### 手順 3-2: Conditional Mean-Flow 小型 DiT の学習

1. **モデル構造**:
   パラメータ数 `100M〜300M` の小型 Latent DiT。入力は：
   - ノイズ時刻 $(r, t)$ と区間補間された現在チャンク潜在 $z_t$
   - 直前チャンク末尾フレームに軽微なノイズ $\tau \in [0.05, 0.25]$ を加えた条件潜在（自己回帰ドリフト耐性のため学習時にノイズ注入＝ノイズオーグメンテーションを行う）
   - 目標カメラ軌道のピクセル単位 Plücker 光線マップ（潜在解像度に縮小してチャンネル結合）
   - 近傍 $K$ 枚の Mini-UVE シーントークンへの Cross-Attention
2. **MeanFlow 目的関数（Geng et al., 2025）**:
   瞬間速度 $v(z_t, t) = z_1 - z_0$ に対し、時間区間 $[r, t]$ の平均速度 $u_\theta(z_t, r, t, \text{cond})$ を予測させ、MeanFlow 恒等式
   $$u_{\text{tgt}} = v - (t - r)\left(v \cdot \partial_z u_\theta + \partial_t u_\theta\right)$$
   の stop-gradient ターゲットに対する回帰損失で学習する。これにより教師モデルの追加蒸留なしで **1-NFE（$r=0, t=1$）〜 2-NFE** 生成を行う。

### Stage 3 特有の技術的罠と分岐

| 発生しうる問題 | 分岐・回避策 |
|---|---|
| **C-trap-1（JVP と Attention カーネルの非互換・VRAM 倍増）**: PyTorch の `torch.func.jvp`（順伝播自動微分）が FlashAttention / Memory-Efficient SDPA カーネルで未対応エラーになる、または math SDPA に切り替えた途端に VRAM が溢れる | ① JVP を計算するサンプル割合をバッチの 25% に絞る（MeanFlow 論文でも有効とされる手法）＋チャンク長を 9 フレームに短縮する。<br>② それでも VRAM 上限を超える場合は、JVP を使わず 2 回の順伝播の自己整合性だけで 1〜2 NFE 化する **Shortcut Models（Frans et al., ICLR 2025）** または **2-step Rectified Flow (Reflow)** 損失へ切り替える。 |
| **C-trap-2（カメラ光線への追従不良・ぼけ）**: 推論時は `PLATEAU++` メッシュを描かないため、未知の俯瞰角度で建物が溶ける（`skyline_iou < 0.85`） | 完全メッシュレスを諦め、C 製ラスタライザ `raster.c` が CPU で数ミリ秒で出せる **低解像度（`80×45`）の PLATEAU 深度マップ 1 枚だけ** を潜在チャンネルに足す（「超軽量ジオメトリヒント付き Reality View」への縮退）。それで `skyline_iou >= 0.90` に回復すれば合格とする。 |
| **C-trap-3（24 GPU 時間以内に収束しない）**: 表現力または軌道データ数不足で実用画質に届かない | **Stage 3 のみ撤退**し、Stage 2（経路 B または B-2）の成果物をこのプロジェクトの最終到達点として **Stage 4** へ進む。 |

## 5. 撤退基準（Kill Criteria）と撤退時の手順

「もう少しエポックを回せば」「別のプロンプトやハイパーパラメータを試せば」と際限なく資源を溶かすことを防ぐため、以下の **5 項目の撤退基準（R1〜R5）** を設けます。該当し、かつ上に書いた 1 回の規定フォールバックでも解消しなかった時点で、直ちに実験を打ち切ります。

| ID | 項目 | 撤退と判定する定量的・客観的基準 |
|---|---|---|
| **R1** | **計算資源・速度の上限** | ・推論（解像度 `832×480` 最小構成、量子化や 1〜4 NFE 適用後）が **1 フレームあたり 5.0 秒を超える**（10 秒の試作確認に 20 分以上かかり反復実験が成立しない）。<br>・Stage 2 または Stage 3 の学習が、ホストの資源制限下で **延べ 24 GPU 時間** 回しても検証損失が下げ止まり、目視可能な構造を結ばない。<br>・バッチサイズ 1＋勾配チェックポイントでも OOM が解消しない。 |
| **R2** | **幾何・地理構造の崩壊** | `eval_tracks.py` の `track_elevated` / `track_interp` において、PLATEAU 正解シルエットとの **`skyline_iou` 平均が `0.85` 未満**、または交差点の道路本数・進行方向の建物配置がフレーム進行とともに変形・消失する（実在地理を扱うリポジトリとして許容不可）。 |
| **R3** | **時間的一貫性の破綻** | 240 フレーム（10 秒）の自己回帰生成で、先頭と末尾の輝度・彩度変化率 **`color_drift` が 25% を超える**（白飛び・黒潰れ・単色化）、または静止領域の再投影誤差 **`warp_rmse` が現行ベースラインの 1.5 倍を超え**、かつ分岐 B-2（3D 書き戻し）でも解消できない。 |
| **R4** | **既存ベースラインに対する優位性不在** | `holdout_cams.json`（未見の 6 視点）において、**`holdout_lpips` が現行の決定論的ベースライン（`PLATEAU++ v0.1.0` + `world_model` アトラス逆算）を 0.03 以上改善しない**、かつ `track_extrap` の等倍目視で「未観測面が埋まる利点」より「実写で読めていた看板・窓割が潰れる欠点」の方が大きいと判断される。 |
| **R5** | **ライセンス・再現性の不成立** | 上記 R1〜R4 を満たせるモデルが非商用ライセンス・再配布制限付きのものしか存在しない、または乱数シードと入力を固定して 2 回書き出した際にフレーム間の差が大きく再現性を担保できない。 |

### 撤退時の凍結手順（Clean Exit）

1. `out/` の一時生成物や巨大な重みファイルを整理し、リポジトリに不要なコードや未テストの変更を残さない（`packages/` には一切手を入れない）。
2. [README.md](README.md) に「撤退報告」節を追記し、次を記録してコミットする：
   - 抵触した撤退基準 ID（R1〜R5）と実測値（`skyline_iou`、`holdout_lpips`、`warp_rmse`、秒/フレーム、ピーク VRAM）。
   - ボトルネックの切り分け（計算量不足か、静止画データからの学習限界か、基盤モデルの都市表現力不足か）。
   - 再開条件（例: 「VRAM XX GB 以上の環境」「Apache-2.0 の軽量 3D 制御 MeanFlow モデルの公開」「歩行・車載の連続 CC0 動画データの確保」など、何が揃えば再挑戦に値するか）。

## 6. Stage 4: 合格時の仕上げ・検品・共通パッケージへの還元判断

経路 A・B・C のいずれかがすべての基準をクリアした場合のみ、次の手順で締めくくります。

1. **再現性の検証**:
   同じシード・同じ入力から `track_elevated` を 2 回書き出し、フレーム一致（または許容誤差内の数値一致）を確かめる。
2. **動画検品と通常速度での目視**:
   書き出した MP4 に対して `packages/pipeline/video/frame_check.py` / `video_qa.py` を通し、通常速度で再生してカメラの加減速・境界・看板・路面の違和感がないか確認する。
3. **出典の完全記録**:
   使った PLATEAU データ、地理院タイル、OpenStreetMap、`photo_guard` を通過した全参照写真の作者・ライセンス、および使用した生成モデル名・作者・ライセンスを `credits.json` に出力する。
4. **`packages/pipeline` への昇格判断**:
   渋谷以外のもう 1 地区（例: `projects/2026/11/26/plateau-pp/areas.json` の西新宿 `shinjuku` または福生 `fussa`）でも同じ手順が破綻なく動くことを確かめてから、初めて `packages/pipeline/` へ単体テスト付き（1 ファイル 400 行以内）で移植する。渋谷 1 地区でしか動かないうちは、このプロジェクトディレクトリ内に留める。
